# Realtime Stock Simulator

**Student:** Yi He

Realtime Stock Simulator is an INFOSCI 102 final project that implements a small realtime stock-trading game. The player chooses a difficulty level, watches a simulated stock price move over time, buys and sells shares, and tries to reach the target asset value without falling below the loss limit. The project can run in Google Colab, Jupyter Notebook, or as a normal Python desktop GUI.

## What I Built

I built a Python stock simulator with a random price engine, portfolio accounting, Easy/Normal/Hard difficulty settings, automatic chart updates, trading controls, restart/main-menu controls, win/loss conditions, and end-game data output for normal Python mode.

## How To Run The Project

Clone or download the repository, then install dependencies:

```bash
pip install -r requirements.txt
```

Run as a normal Python desktop GUI:

```bash
python realtime_stock_simulator_skeleton.py
```

Run in Jupyter Notebook:

```python
from realtime_stock_simulator_skeleton import create_simulator

game = create_simulator()
```

Run in Google Colab:

1. Upload `realtime_stock_simulator_skeleton.py` to the Colab runtime, or clone/download this repository in Colab.
2. Run the same notebook code:

```python
from realtime_stock_simulator_skeleton import create_simulator

game = create_simulator()
```

Expected runtime is under 10 minutes. The project starts immediately after dependencies are installed. In all environments, choose a difficulty, enter a share quantity, and use the buttons to buy, sell, pause, restart, or return to the main menu.

### Selected Prompt-Response Pairs

#### Pair 1: Notebook And Colab Auto-Update Failure

Prompt:

```text
The game is designed to run in Google Colab or Jupyter Notebook, but after selecting difficulty nothing happens and the chart cannot update automatically. Find the problem first without modifying code.
```

AI response summary:

The AI identified that the code mixed `clear_output()`, widget callbacks, Matplotlib rendering, and background threading. It explained that Jupyter may tolerate this better than Colab, while Colab often delays or buffers widget updates from Python-side loops.

Critical review:

The diagnosis was useful, but the first fix still did not fully solve Colab auto-updating. I tested it and reported that Colab still failed. The final solution required a Colab-specific callback/timer approach instead of relying only on Python threads or asyncio.

#### Pair 2: Normal Python GUI Support

Prompt:

```text
Add a graphical interface for normal Python execution. Widgets do not seem suitable for normal Python, so use another visualization method.
```

AI response summary:

The AI suggested using Tkinter with Matplotlib's Tk canvas and Tkinter's `after()` timer for GUI-safe updates.

Critical review:

This was a good direction because it avoided using notebook-only widgets in normal Python. I kept the backend game logic separate and used a different frontend update method for Python GUI mode.

#### Pair 3: Total Assets Jump Bug

Prompt:

```text
Re-check the total assets calculation. During gameplay, total assets sometimes jumps from around 7000 to 13000.
```

AI response summary:

The AI found that `totalAssets()` itself was correct, but `dynamicDifficulty()` called `applyDifficulty()`, which reset `portfolio.cash` during gameplay. This made total assets jump suddenly.

Critical review:

The AI correctly traced the bug to the interaction between dynamic difficulty and difficulty application. The fix was to separate full difficulty initialization from market-only difficulty updates.

#### Pair 4: GitHub And Submission Files

Prompt:

```text
Create a GitHub-ready project folder without modifying the original source code. Add README.md, requirements.txt, .gitignore, initialize Git, and prepare the repository for upload.
```

AI response summary:

The AI created a separate repository folder, copied the source file, added supporting files, initialized Git, and explained how to commit and push.

Critical review:

The repository setup was useful, but I still needed to configure Git identity and network proxy settings myself before pushing to GitHub.

## Review And Correction Record

1. Colab update strategy correction:

The AI initially tried to make Colab work using Python-side background execution patterns. Testing showed that Colab still did not update live and instead delayed output. I identified this behavior from runtime testing, and the implementation was corrected to use Colab's frontend callback mechanism with `google.colab.kernel.invokeFunction()`.

2. Win/loss logic correction:

The game originally checked win/loss during automatic price ticks. I identified that this ended the game while the player was still holding unsold shares. I changed the design so automatic price movement does not decide win/loss by itself; instead, win/loss is checked after selling, matching the intended realized-trading gameplay.

3. Dynamic difficulty cash-reset correction:

The AI helped locate the source of the total asset jump, but I had to reason through the design distinction between initial difficulty setup and in-game market adjustment. The correction was to add a market-only difficulty application path so dynamic difficulty no longer resets cash.

4. Main Menu versus Restart correction:

The AI first implemented restart as "restart current difficulty." I clarified that I also wanted a separate Main Menu action that returns to the initial tutorial and difficulty selection state. The interface was then updated to include both behaviors.

## Reflection

AI accelerated the project by helping me inspect code paths, compare environment-specific behavior, and generate focused implementation changes. It was especially useful for separating the frontend implementations for Colab, Jupyter, and normal Python while keeping shared backend logic. It also helped with documentation and GitHub preparation.

At the same time, AI suggestions required careful testing and correction. Some early fixes were incomplete for Colab, and some design choices needed my own judgment, such as when win/loss should be checked and how restart should differ from returning to the main menu. If I repeated the project, I would define the gameplay rules earlier and write small tests for state transitions like dynamic difficulty, selling, restart, and main-menu reset before building the UI layers.
